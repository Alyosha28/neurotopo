# Experiment protocol

For a new **project Gate 1-motivated benchmark qualification**, register the candidate update or named reference K factor and its falsifying ablation **before** searching for control headroom. Name the actual proposed matched primary control, resource costs, whether a simple explicit filter/cache explains the task, the falsifiable reason the K factor could improve under matched resources, and a success/failure/borderline decision table. A task-only screen without a candidate may be legitimate independent benchmark research, but must have its own purpose, finite resource budget and outcome-dependent decision; it cannot by itself qualify a later unspecified Gate 1 architecture. This candidate-first order is prospective after STR-0002 (`research/decisions/0022_candidate_first_gate1_calibration.md`); it does not rewrite earlier experiments or forbid separately registered benchmark science.

Under `gate1_candidate_first_v1`, the JSON entry contract is a **structural QUESTION gate**; `PRIOR_ART` and independent `CRITIQUE` still judge the substance. A `reference_k` factor may enter as `field_reference`; its project Gate 1 score is `PROJECT_ELIGIBILITY_UNRESOLVED` until a prospective eligibility decision. Before any candidate-driven task screen, freeze a finite task menu and maximum number of attempted configurations, retain every failed and borderline attempt, and reserve evaluation tasks/seeds not used to select the benchmark. Selected-task success alone is exploratory until the prespecified held-out check; do not let candidate-first become candidate-favoring task search. The entry contract records separate state, parameter and executed-compute plans, not a claim that these are already matched.

1. Freeze one question, causal link, prior-art overlap and strongest rejection reason in `experiments/EXP-XXXX/vN.md` plus a machine-readable JSON registry record (JSON is an allowed YAML subset).
2. Declare baseline semantics, interventions, controls, data generator version, split seeds, training samples/updates, initialization seeds, primary/secondary outcomes, inference steps, resource tolerances, exclusions and decision rule before scientific implementation/run. Deviations create vN+1, retaining vN.
3. Before promoting a new benchmark, derive its minimal sufficient statistic and simple algorithmic solution. Calibrate both a strong conventional baseline **and the proposed primary matched control** on separate streams using a proper score against the exact/bounded oracle; noisy true labels do not establish architecture headroom. Preflight must compare the planned useful-effect threshold with the primary control's oracle-relative error: for nonnegative loss, improvement greater than that error is impossible on that calibration condition. Use independent final seeds/streams after difficulty is frozen. Verify recurrence equivalence, masking, deterministic generation, counterfactual prefixes, no future leakage, shape/gradient behavior, tiny overfit and resource accounting. Sanity tests are not scientific findings. Do not select a configuration by final test performance.
   Freeze the primary control's identity and inclusion rule before calibration, based on the causal claim and closest competing mechanism. List each relevant strong prior-art control with an inclusion or exclusion reason before viewing its performance; if a separate prior-art-increment claim is primary, calibrate headroom against **that claim's** actual primary control as well. A control may be excluded for a stated mismatch, but not because it scores too well on the eventual endpoint.
   Name the actual causal factor separately from the model package. For a prior-art particle/RIM comparison, prespecify whether the estimand is the whole architecture's task effect or an isolated trajectory-count/routing/resampling factor; the latter requires targeted ablations and state/compute-aware controls. An overall PF-GRU versus GRU win, even with resource matching, does not isolate the effect of trajectory count.
4. Run immutable config. Save config and source hashes, Git commit and dirty status, package versions, hardware, seed, dataset identity, runtime, effective and allocated parameters, dynamic state, operation counts, memory estimate and latency. FLOP proxies must say what is omitted; do not call a proxy a measurement.
5. Treat initialization/training seeds as replication units. Use paired seed differences on shared held-out data; pairs inside a seed are not independent replications. Report every seed, effect size and uncertainty, including variance and failures. Label secondary/exploratory comparisons. Never silently replace failed seeds.
6. Distinguish active connections and dense allocated weights; sparse masks with dense kernels do not save executed FLOPs. Track recurrent hidden state, retained pre-query readout cache and gate workspace separately. The pre-query readout does not feed back into the recurrence but remains live until the model returns; neither that cache nor gate workspace is a measured peak-memory estimate. Log measured latency, state bytes and parameter bytes; if peak memory or full training FLOPs are unavailable, mark unavailable with reason.
   If a learning curve is used for sample- or compute-efficiency claims, record cumulative examples, tokens, updates, measured wall time and a clearly scoped executed-compute estimate **at each evaluated checkpoint**. A full-run total repeated beside early checkpoints cannot establish per-checkpoint cost matching.
7. Report the simplest alternative explanation and adversarial review. Keep engineering validation, benchmark qualification and architecture effect separate. When headroom/learning guards fail, still report the fixed-test effect estimate and its mathematical bound if applicable, while retaining the pre-registered four-way decision; neither an `INCONCLUSIVE` label nor a tiny interval alone expresses the whole scope. A benchmark result does not establish semantic specialization, attractor escape, SAE, biological advantage or broad architecture superiority.
8. Commit frozen source/config before a formal run; output manifests capture hashes. Reproduce from an isolated checkout with only the experiment and command. Keep failed/negative results and stage-gate decisions in repository. Updating prose after results must not overwrite registered thresholds.
9. After `DECIDED`, send only the registered design and analyzed action output to a fresh-context reflector. Verify every cited issue, record a reasoned main-agent reaction with concrete action evidence, then open the next iteration. See `docs/post_task_reflection.md`.

## Novelty guardrail
Before any mechanism claim: is it implemented already or under another name; is the difference architectural; is it measurable; can an ablation isolate it? If unresolved, record a candidate, not a contribution.
